Across 27 tracked applications the pattern is proven: stack keywords (dbt, Airflow, Snowflake, EDI) decide screening, and Temitope's packets claim only what he can prove — dbt/Airflow were claimed NOWHERE on the evermore packet, EDI nowhere on VIVA, by deliberate honesty. Build A closes the two highest-value gaps FOR REAL: it builds working dbt + Airflow artifacts on his own public PFAS dataset, so the claims become true and linkable, and it adds a claim-verifier so no future packet ever over- or under-claims. Build B upgrades the auction operation that already runs Mon/Wed/Fri.

Versioned JSON `proof-registry.json`: every entry = {artifact_id, kind (dbt_model|dag|sql_pack|dax_library|dashboard|report), title, repo_path, evidence (command run + result + timestamp), supports_claims: [exact claim strings], source_urls}. ## BUILD A — Job-Hunt Portfolio Factory
- **A1. Ingest:** EPA UCMR 5 occurrence data → NC extract in a local DuckDB warehouse; row counts reconciled against the EPA source file; ingest is a repeatable script, not a one-off.
- **A2. dbt project (`pfas_warehouse/`):** dbt-core + dbt-duckdb. Staging → intermediate → marts: `mart_county_scorecard` (per-county systems, detections, screening-vs-benchmark flags), `mart_analyte_summary`, `mart_system_screening` (system-level results vs 2024 MCL benchmarks, screening language enforced in column names/comments — no "violation" anywhere). Schema tests + data tests (non-negative concentrations, benchmark arithmetic, referential integrity). `dbt docs generate` output committed. README with the exact commands to reproduce.
- **A3. Airflow orchestration (`dags/pfas_pipeline.py`):** local Airflow, one DAG: ingest → dbt run → dbt test → publish a one-page run summary (rows, tests passed, top screening counties). Must demonstrate: one clean end-to-end run, one backfill for a prior period, retries configured. Failure of dbt tests must fail the DAG (no silent publish).
- **A4. SQL + BI proof pack:** (a) `sql/` — 8–10 advanced SQL patterns (window functions, gaps-and-islands, incremental merge logic) implemented against the marts, each with a header naming the JD keyword it evidences; (b) `snowflake/` — the mart queries translated to Snowflake dialect + a load script, clearly labelled dialect-only unless run; (c) `powerbi/` — a DAX measure library (screening rates, benchmark ratios, YoY deltas) + semantic-model spec (tables, relationships, measures) as reviewable code/text; (d) an interactive HTML dashboard rendered from the marts (county screening explorer) as the visual proof.
- **A5. Packet claim-verifier (`verify_packet.py`):** inputs = a JD (text/URL) + a packet (resume + cover letter, docx/txt/md). Extracts skill/experience claims; verdict per claim: PROVEN_BY_ARTIFACT (registry id) / IN_BASE_DOCS / UNSUPPORTED (must remove or soften) / FORBIDDEN (citizenship, clearance, employer-proprietary). Output: a claim-by-claim table (md + json). Must pass the evermore packet exactly as submitted (dbt/Airflow absent = correct) and must catch planted unsupported claims in a synthetic packet (builder creates the synthetic; Muse holds the answer key at shadow run).
- **A6. JD gap analyser (`gap_report.py`):** for a set of JDs, extracts required skills, diffs against registry + base docs, outputs ranked gaps (frequency × target-role weight). Seed corpus: capture LIVE at build time from official pages — Centene Data Analyst III (1672733-1), Genworth/CareScout Data Analyst (REQ-260438), Bureau Veritas Senior Sustainability Consultant (214408); any posting already closed is recorded as CLOSED with the capture date, never reconstructed from memory or aggregators.
- **Repo shape:** the whole Build A output is one git-ready repo (`portfolio-factory/`) with a top README written for a hiring manager: what it proves, how to run it, links to docs/dashboard. (Publishing to GitHub is Temitope's step, outside the sprint.)

## BUILD B — Auction Intelligence v2
Extends the live dashboard operation (auctions.tossonanalytics.com, Mon/Wed/Fri refresh). Read-only against every marketplace: no bids, no account changes, no purchases — analysis and alerts only.
- **B1. Manifest ROI analyser:** parses Liquidation.com / B-Stock manifest CSVs (owner-staged samples + format adapters) → per-lot landed cost (price + fees + shipping estimate) and resale-comp range (owner sold-history if staged, else labelled public-comp mode) → verdict bands (STRONG / MARGINAL / PASS) with the arithmetic shown. Must reproduce a hand-checked verdict on one sample lot (Muse verifies at shadow run).
- **B2. HiBid churn tracker:** across refresh snapshots, detects re-listed lots (title similarity + image hash where available) and price deltas on watched categories; outputs a churn report (new / re-listed / price-up / price-down) per cycle. A planted re-list in test snapshots must be caught.
- **B3. Land parcel scorer:** for the land program (1–5 acres, Caswell/Rockingham/Person counties, cash < $30k; plus the ≤$5k auction track) — scores candidate parcels/listings on owner criteria (acreage, price, road frontage, zoning signal, distance from Mebane) from public county/auction sources; EVERY emitted find carries its own direct URL (owner's standing rule; uncapturable = "URL not captured", never a search link). Fail-closed: a parcel missing price or acreage is excluded and counted, never estimated.
- **B4. Kia Carnival checker (SEPARATE module — never merged into the general auction flow):** for 2022+ Carnival listings: VIN decode, NHTSA recall check incl. SC266 sliding-door, trim filter (EX/SX pass; VIP Lounge trims flagged out), and a finance-clause scanner stub for the summer-2027 KFA strategy (no-minimum-term + prepayment-penalty checks as a document checklist generator). Monitor mode only.
- **B5. Runbook + integration notes:** how each module plugs into the existing Mon/Wed/Fri refresh and the closing-<48h ping, without changing the dashboard's current behaviour.
